# Running in a sandboxed container

You are running inside the `claude_in_container` Docker sandbox, not on the user's host.

- **Writable paths:** only `/workspace` (your current directory, bind-mounted to the host project), `/home/claudeuser` (bind-mounted to `claude_home/` on the host, where login state persists), and `/tmp` (in-memory, wiped on container exit). The rest of the filesystem is read-only.
- **You only see `/workspace` and `/home/claudeuser`.** The files that launched you — `claude.sh`, `docker-compose.yml`, `Dockerfile`, and the repo-root `.env` (holding `CLAUDE_CODE_OAUTH_TOKEN` / `GITHUB_TOKEN`) — live on the host outside the mount. Treat `.env`, the wrapper, and `docker compose` as host-side: ask the user instead of reading or running them yourself.
- **No root, no capabilities:** you cannot `sudo`, install system packages (`apt`, `apk`, etc.), or modify anything outside the writable paths.
- **Network:** unrestricted by default, but in hardened mode (`HARDENED=1`) outbound traffic is allowlisted to a small set of hosts (`api.anthropic.com`, `github.com`, `registry.npmjs.org`, …). In hardened mode, unexpected DNS or TLS failures usually mean the host isn't on the allowlist; in default mode they're more likely a CA-bundle or transient network issue.
- **GitHub access:** `GITHUB_TOKEN` is only set if the user opted in via `.env` — check `printenv GITHUB_TOKEN` before assuming. When present, the container's default `~/.gitconfig` rewrites any SSH GitHub URL (`git@github.com:owner/repo`) to HTTPS and supplies the token at request time, so plain `git clone`, `git pull`, and `git push` work against GitHub with no URL surgery. If `GITHUB_TOKEN` is not set, don't attempt to push or access private repos — tell the user to either set `GITHUB_TOKEN` in `.env` (README has the walkthrough) or push from the host. For non-GitHub hosts (GitLab, Bitbucket, self-hosted) the rewrite is not active by default — see `~/.gitconfig` for the pattern to extend.
- **Opening a PR:** there is no `gh` in the image. Use `curl` against the GitHub API with `$GITHUB_TOKEN`, e.g. `curl -sS -X POST -H "Authorization: Bearer $GITHUB_TOKEN" -H "Accept: application/vnd.github+json" https://api.github.com/repos/<owner>/<repo>/pulls -d '{"title":"...","head":"<branch>","base":"main","body":"..."}'`. Push the branch first. This needs `GITHUB_TOKEN` set (see above) with `Pull requests: Read & write` scope.
- **Git identity:** before your first commit, run `git config --get user.email` to confirm one is set (the wrapper usually copies the host's identity into `~/.gitconfig.local` on first run). If it's empty, stop and tell the user to set `git config --global user.{name,email}` on the host and re-run, or create `claude_home/.gitconfig.local` with a `[user]` block. Do NOT invent a default like `claudeuser@<hash>` or set `user.email` repo-locally to work around it.
- **Need a missing tool** (e.g., `python3`, `make`, `go`, a linter)? Don't try to install it — it will fail. Instead, tell the user to add it to the `Dockerfile` on the host (typically the `apt-get install` line), rebuild with `./claude.sh build` (or `cic build` if they installed the launcher), then restart the session. See the "Extending the container (advanced)" section of `README.md` for details.
- **Don't try to use `docker` itself from inside the container.** Giving the sandbox Docker access would defeat the whole sandbox; if the user needs container builds, they run them on the host.
